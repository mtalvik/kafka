# Kafka Streams DSL: KStream, KTable, GlobalKTable

## 1. Область

Этот урок про высокоуровневый **DSL** Kafka Streams: две основные абстракции (`KStream`, `KTable`), их глобальный вариант (`GlobalKTable`) и построенные на них операции — stateless-преобразования, агрегации, оконность и соединения. Processor API (низкоуровневая топология, кастомные state store, punctuator) — отдельный урок.

Лаба идёт против брокера на EC2 `kafka` (KRaft, один узел, SASL/PLAIN), а не против локального Docker-стека. Это меняет две вещи по сравнению с эталонным материалом: приложению нужен SASL-конфиг клиента, и каждый внутренний топик, который создаёт Streams, наследует replication factor брокера — см. раздел 8.

## 2. Двойственность потока и таблицы

Топик можно читать двумя способами, и выбор — семантический, а не косметический.

- **`KStream`** — каждая запись это независимый факт. Две записи с одним ключом это два события, оба сохраняются. Семантика: **INSERT**. Чтение потока кликов, лога транзакций, потока с датчика.
- **`KTable`** — каждая запись это *текущее значение* для своего ключа. Более поздняя запись с тем же ключом **заменяет** предыдущую. Семантика: **UPSERT** (а значение `null` это **DELETE**, tombstone). `KTable` это материализованное представление «последнее-значение-на-ключ», подкреплённое локальным state store.

Эти двое — двойственны. Таблица это снимок потока, свёрнутого по ключу; поток это changelog таблицы. По changelog `("alice",1) ("charlie",1) ("alice",2) ("bob",1)` таблица эволюционирует `{alice:1} → {alice:1,charlie:1} → {alice:2,charlie:1} → {alice:2,charlie:1,bob:1}`. Проигрывание changelog восстанавливает таблицу точно — именно поэтому материализованный `KTable` можно перестроить из его changelog-топика после падения.

**Таблица как сжатый топик.** Модель «KTable это сжатый топик» полезна: log compaction оставляет только последнее значение на ключ, что и есть представление-таблица. Две оговорки, которые стоит проговорить студентам:

> **Correction to a common slide.** Материализация `KTable` из исходного топика **не** требует, чтобы у этого топика было `cleanup.policy=compact`. Можно построить `KTable` над обычным топиком с retention; Streams всё равно сворачивает по ключу в state store. Компакция это *аналогия*, и реальная гарантия она только для внутреннего **changelog**-топика, который Streams создаёт для материализованной таблицы — вот он сжимается, чтобы store можно было восстановить.

## 3. Кэширование KTable и частота эмита

`KTable` не обязательно эмитит запись дальше по потоку на каждую входную запись. Обновления сначала проходят через record cache; дальше проходят только некоторые.

- Больше входной пропускной способности → чаще эмит.
- Больше уникальных ключей → чаще эмит (меньше выгоды от дедупликации).
- Эмит также случается на коммите и когда кэш заполняется и сбрасывается в state store.

Кэш дедуплицирует: если ключ `YERB` обновлён дважды между сбросами, дальше уходит только последнее значение — промежуточное никогда не сохраняется и не эмитится. Это оптимизация пропускной способности, а не гарантия корректности, и это значит, что **нельзя полагаться на то, что увидишь дальше по потоку каждое промежуточное обновление** из KTable.

> **Correction to a common slide.** `cache.max.bytes.buffering` **устарел** (KIP-770, Kafka 3.4) в пользу `statestore.cache.max.bytes`. На клиенте 4.x старое имя ещё работает, но пишет warning про deprecation; используй новое. Чтобы в демо видеть каждое обновление, поставь кэш в `0` — не подавай старое имя конфига как актуальное.

`commit.interval.ms` управляет частотой flush/commit. По умолчанию `30000` мс, но падает до `100` мс автоматически при `processing.guarantee=exactly_once_v2`. Это взаимодействует с кэшированием: при включённом EOS эмит гораздо чаще даже при том же размере кэша.

## 4. Агрегации

`groupByKey()` (ключ не меняется) или `groupBy()` (новый ключ, вынуждает репартиционирование) превращает `KStream` в `KGroupedStream`, над которым агрегируешь:

- **`count()`** — число записей на ключ.
- **`reduce(v1, v2 -> v)`** — комбинирует два значения **одного** типа. Смены типа нет.
- **`aggregate(initializer, (k, v, agg) -> agg')`** — общий fold; агрегат может быть **другого** типа, чем вход (`Initializer` даёт ноль). Используй, когда считаешь в структуру, суммируешь в объект и т.д.

Все три возвращают `KTable` — текущий агрегат это представление «последнее-значение-на-ключ».

Группировка **таблицы** даёт `KGroupedTable` с похожим интерфейсом, минус `windowedBy`. Одна асимметрия, которую слайды пропускают и на которой люди спотыкаются:

> **Correction to a common slide.** `KGroupedTable.aggregate` и `reduce` принимают **две** функции, **adder и subtractor**. Поскольку обновление таблицы заменяет предыдущее значение, агрегат должен сначала *вычесть* старый вклад этого ключа, а потом *добавить* новый. У `KGroupedStream` subtractor-а нет — записи потока это инсёрты, откатывать нечего. Показ агрегации таблицы одной функцией даёт неверный результат на обновлениях.

`groupBy`, меняющий ключ, пишет во внутренний **repartition**-топик и читает его обратно, чтобы новый ключ попал на правильную партицию. Это автоматически, но не бесплатно — это реальный сетевой и дисковый I/O.

## 5. Оконность

Не-оконная агрегация идёт вечно по всей истории. Оконность ограничивает её во времени события: «операций на тикер за 10 минут», «кликов на баннер за 20 минут», непрерывно обновляясь. В Kafka Streams четыре типа окон.

| Окно | API | Перекрытие | Определяется |
|---|---|---|---|
| Tumbling (кувыркающиеся) | `TimeWindows.ofSizeAndGrace(size)` | нет | фиксированный размер, advance = size |
| Hopping (прыгающие) | `TimeWindows.ofSizeAndGrace(size).advanceBy(hop)` | да, если hop < size | фиксированный размер + интервал сдвига |
| Sliding (скользящие) | `SlidingWindows.ofTimeDifferenceAndGrace(diff)` | да | макс. разница во времени между записями |
| Session (сеансовые) | `SessionWindows.ofInactivityGapAndGrace(gap)` | по данным | интервал бездействия между записями |

> **Correction to a common slide.** Эталонный слайд называет «20-секундное окно, сдвигающееся каждые 5 секунд» **скользящим** (sliding). В DSL Kafka Streams это **прыгающее** (hopping) окно (`TimeWindows...advanceBy`). Настоящее `SlidingWindows` (KIP-450, с 2.7) это не фиксированный сдвиг — оно определяется максимальной *разницей* во времени между двумя записями и выровнено по таймстампам записей, порождая границу окна вокруг каждого события. Студент, который потянется за `SlidingWindows.ofTimeDifference...` в ожидании 5-секундного сдвига, получит другую семантику. Держи четыре имени раздельно: tumbling = advance равен size; hopping = фиксированный advance; sliding = разница во времени; session = интервал бездействия.

Две вещи, которые слайды опускают, но которые должны быть в лекции:

- **Grace period.** Каждая оконная операция принимает grace-период (`...AndGrace(Duration)`). Поздние записи в пределах grace всё ещё обновляют своё окно; за пределами grace они отбрасываются. Оконной агрегации без решения про grace не бывает — API вынуждает сделать это явно.
- **Suppression.** По умолчанию оконный KTable эмитит промежуточные результаты по мере заполнения окна. `suppress(Suppressed.untilWindowCloses(...))` придерживает вывод, пока окно не закроется плюс grace, так что дальше уходит один финальный результат на окно вместо потока промежуточных. Так получаешь «одно число на 10-минутный бакет».

Оконная агрегация ключуется `Windowed<K>` (исходный ключ + границы окна), а у её changelog/store retention завязан на размер окна + grace.

## 6. Соединения (Join)

Жёсткое предусловие для join-ов `KStream`/`KTable` — **co-partitioning**: обе стороны ключуются одинаково, одинаковое число партиций, одинаковая стратегия партиционирования. Если ключи не ложатся на одну партицию, совпадающие записи никогда не встретятся. Streams репартиционирует автоматически, когда может обнаружить смену ключа; несовпадение числа партиций он не чинит — это на тебе.

| Join | Inner | Left | Outer | Оконный |
|---|---|---|---|---|
| KStream–KStream | да | да | да | да (обязателен) |
| KStream–KTable | да | да | — | нет |
| KTable–KTable | да | да | да | нет |
| KStream–GlobalKTable | да | да | — | нет |

Матрицу стоит запомнить: **outer есть только у stream–stream и table–table**; stream–table и stream–global это lookup-ы, для них outer бессмыслен (нечего эмитить для правой строки без события в потоке).

- **KStream–KStream** оконный — два события «соединяются», только если попадают в join-окно друг друга. Нужен `JoinWindows`.
- **KStream–KTable** это lookup: каждое событие потока обогащается текущим значением таблицы для своего ключа. Окна нет.
- **KStream–GlobalKTable** — см. следующий раздел; ключевое отличие — нет co-partitioning и есть `KeyValueMapper` для выбора ключа поиска.

## 7. GlobalKTable против KTable

`KTable` **партиционирован**: каждый таск держит только шард таблицы для тех партиций, которыми владеет. Поэтому join против KTable требует co-partitioning — совпадающий ключ должен быть в том же таске.

`GlobalKTable` **полностью реплицирован**: каждый экземпляр приложения на старте грузит **все** партиции топика в локальный store. Следствия:

- **Нет co-partitioning для join-ов.** Join `KStream–GlobalKTable` использует `KeyValueMapper`, который извлекает ключ поиска из записи *потока*, а затем ищет его в полной локальной копии. Поток **не** нужно перекл��чевать или репартиционировать — в этом весь смысл.
- **Только чтение.** GlobalKTable поддерживает join-ы и ручные lookup-ы (через store) и больше ничего — ни агрегаций, ни дальнейших stateful-преобразований.
- **Цена.** Каждый экземпляр держит всю таблицу и должен загрузить её до начала обработки. Годится для маленьких, медленно меняющихся справочных данных (коды валют, названия компаний, feature flags); плохо для больших или быстро меняющихся.

Классическое применение: обогащающий join, где переключение ключа основного потока только ради co-partitioning вызвало бы несколько репартиционирующих кругов. `selectKey` перед join-ом с KTable пишет в repartition-топик и читает обратно каждый раз; со справочными данными, достаточно маленькими для репликации, GlobalKTable убирает всё это.

## 8. Внутренние топики и ловушка одного узла

Streams молча создаёт внутренние топики: **repartition** (для операций, меняющих ключ) и **changelog** (для подкрепления материализованных store-ов), все с префиксом `application.id`.

> **Correction to a common slide / ловушка лабы.** Эти внутренние топики создаются с `StreamsConfig.REPLICATION_FACTOR_CONFIG` (`replication.factor`), у которого дефолт `-1` = «использовать дефолт брокера». На одноузловом брокере лабы, если у брокера `default.replication.factor` больше 1, **приложение падает на старте при создании внутренних топиков.** Поставь `replication.factor=1` в конфиге Streams явно. Это тот же класс отказа, что `__transaction_state` (урок про транзакции) и `_schemas` (урок про Schema Registry): любой топик под управлением Kafka наследует replication factor, который один брокер не может обеспечить.

Смежные конфиги, которые надо знать: `application.id` (он же id консьюмер-группы и префикс внутренних топиков), `num.stream.threads` (параллелизм внутри экземпляра; всего тасков ≤ числа партиций) и `default.key/value.serde`.

## 9. Запуск на нашей инфраструктуре

Конфиг топологии это объект `Properties`/`StreamsConfig`. Против брокера на EC2 `kafka` он должен нести SASL:

- `bootstrap.servers` → приватный IP брокера:9092
- `security.protocol=SASL_PLAINTEXT`, `sasl.mechanism=PLAIN`
- `sasl.jaas.config` → `PlainLoginModule` с принципалом для streams
- `replication.factor=1` (раздел 8)
- `application.id` уникален на каждое упражнение (у каждого своя группа + пространство внутренних топиков)

ACL для принципала streams: **read** на исходные топики, **write** на топики-приёмники, **read+write** на внутренние repartition/changelog топики (префикс = `application.id`) и доступ к группе для консьюмер-группы. Управляй ими через GitOps Terraform, а не руками.

Сборка через Gradle на EC2 `kafka` (t3.small). Первый `gradle build` тянет пол-интернета и жжёт CPU credits; жди, что один раз будет медленно, а дальше быстро. Упражнения названы `ex1`–`exN` как задачи Gradle.
