# Schema Registry

## 1. Какую проблему решает

Брокер Kafka прозрачен по байтам. Он хранит `key` и `value` как непрозрачные массивы байт и не знает,
что внутри — Avro, JSON, Protobuf или мусор. Это сделано намеренно: брокер остаётся быстрым и простым.
Плата за это — весь груз контракта данных ложится на producer и consumer.

Пока producer и consumer — одна кодовая база, деплоящаяся вместе, это не проблема: они шарят DTO через
версионируемую библиотеку. Проблема появляется в момент, когда стороны деплоятся независимо. Producer
меняет поле — а consumer узнаёт об этом в проде, в рантайме, в 3 часа ночи.

Schema Registry — это внешний арбитр контракта. Он **не часть брокера**: это отдельный сервис с REST API,
поверх compacted-топика `_schemas`, где физически живут все схемы.

## 2. Wire format

Это самая важная механическая деталь, и единственное, что REST/curl-демо показать не может. Когда
producer с Avro-сериализатором пишет запись, на провод уходит **не схема**:

```
[ 0x00 ][ 4 байта: schema ID (big-endian int32) ][ Avro payload ]
 magic    глобальный schema id                      данные, сериализованные БЕЗ встроенной схемы
```

- `magic byte` = `0x00` — версия формата serde.
- `schema ID` — глобальный ID, выданный registry.
- payload — запись, сериализованная **без** собственной схемы. Вот где экономия: standalone Avro-файл
  встраивает схему в каждый файл, здесь — нет.

Consumer читает 5-байтовый префикс, один раз вызывает `GET /schemas/ids/{id}` (дальше кэширует),
получает **writer schema** и десериализует. Если у consumer'а своя **reader schema**, Avro выполняет
schema resolution между writer и reader. Все режимы совместимости существуют ровно для того, чтобы этот
resolution не мог взорваться.

Вывод из раздела: **schema ID в сообщении идентифицирует writer schema — схему, которой данные были
записаны. Это никогда не reader schema.** Один этот факт снимает половину путаницы, с которой студенты
приходят к теме.

> **Correction to a common slide.** На слайдах часто пишут «схема едет вместе с сообщением». Для пути
> через Schema Registry serde это неверно — едут только 4 байта ID. Схема остаётся в registry и
> достаётся по ID. Утверждение «схема едет» верно лишь для сырого Avro container file — а это другая
> сущность.

## 3. Registry, subject, schema ID, version

Четыре сущности, которые склеивают:

- **schema** — сам контракт (определение Avro record).
- **schema ID** — глобальный, уникальный на весь registry (точнее: в пределах одного топика `_schemas`).
  Одна и та же схема, зарегистрированная под двумя разными subject'ами, получает **один** ID.
- **subject** — именованная линия версионирования. Внутри subject'а схемы образуют упорядоченную
  последовательность версий `1, 2, 3…`, и совместимость настраивается per-subject.
- **version** — локальный номер внутри одного subject'а.

Дефолтная naming strategy (`TopicNameStrategy`) даёт **два subject'а на топик**: `<topic>-key` и
`<topic>-value`. То есть у топика `orders` есть `orders-key` и `orders-value`, версионируемые независимо.
На практике key часто примитив (`long`), эволюционирует только `-value`.

ID глобальный (как serial сертификата), version локальная (как «какое это по счёту переиздание вот этого
конкретного CN»). CA-аналогия работает.

## 4. Compatibility

Режим решает, **какое изменение схемы registry примет в момент регистрации**. Проверка идёт на
`register`/`check`, а не в рантайме.

| Режим | Правило | Что разрешено | Кто обновляется первым |
|---|---|---|---|
| `BACKWARD` (дефолт) | новая схема читает данные, записанные старой | добавить optional-поле (с `default`), **удалить** поле | **consumer** |
| `FORWARD` | старая схема читает данные, записанные новой | **добавить** поле, удалить optional-поле | **producer** |
| `FULL` | оба направления | add/remove полей, у которых есть `default` | любой |
| `NONE` | проверок нет | что угодно | никто — ты сам по себе |

Тонкость, которую слайды смазывают: **направление проверки против порядка деплоя.** `BACKWARD` означает,
что новый consumer должен уметь читать старые сообщения, следовательно, обновляешь **consumer первым**.
`FORWARD` — наоборот. Это контринтуитивно и стоит разобрать: при `BACKWARD` можно удалить поле, но
**нельзя** добавить обязательное (без `default`), потому что новый consumer, встретив старое сообщение,
не сможет подставить для него значение.

Варианты `_TRANSITIVE` (`BACKWARD_TRANSITIVE` и т.д.): обычный `BACKWARD` проверяет новую схему только
против **последней** версии; transitive — против **всех** предыдущих. Дороже, но честнее для
долгоживущих топиков, где старые сообщения никогда полностью не вымываются.

## 5. Naming strategies

Развилка: сколько типов record'ов живёт в одном топике.

- `TopicNameStrategy` (дефолт) — один тип на топик. Subject = `<topic>-value`.
- `RecordNameStrategy` — subject = fully-qualified имя record'а. Несколько типов событий в одном топике
  (event sourcing: `OrderCreated` / `OrderShipped` / `OrderCancelled` на одной партиции, с одинаковым
  key, ради сохранения порядка). Один и тот же record в разных топиках маппится в **одну** глобальную
  линию эволюции.
- `TopicRecordNameStrategy` — subject = `<topic>-<record>`. Мульти-тип, но эволюция scoped на топик; один
  и тот же record в топике A и топике B может разойтись.

Мостик к раннему материалу: `RecordNameStrategy` существует не для наведения порядка в именах. Он
существует, чтобы разнородные типы событий делили **одну партицию с сохранением порядка**. Это напрямую
увязывается с лекцией про партиционирование.

Key- и value-стратегии задаются независимо (`key.subject.name.strategy`, `value.subject.name.strategy`);
на практике меняют только value-стратегию.

## 6. Serde flow целиком

**Producer:** объект → serde смотрит на схему → `POST /subjects/{subject}/versions` (или берёт ID из
кэша) → получает ID → пишет `magic + ID + payload`.

**Consumer:** читает 5-байтовый префикс → `GET /schemas/ids/{id}` (кэш) → resolution writer↔reader →
объект.

Кэшируют обе стороны. После прогрева registry не в hot path и не ограничивает throughput.

## 7. Топология: HA против нескольких registry

Два разных смысла слова «много», которые регулярно склеивают:

**Много инстансов = один логический registry (HA).** N процессов Schema Registry за балансировщиком, все
читают и пишут **один и тот же топик `_schemas`**. Пишет (регистрирует) только **leader**; followers
принимают регистрацию и проксируют её лидеру. Все инстансы обязаны иметь одинаковую registry group и один
`_schemas`, иначе — split-brain. Клиент может указать несколько URL в `schema.registry.url`, но это
failover **внутри одного** registry. ID-пространство единое: ID 42 на каждом инстансе значит одно и то
же.

**Много независимых registry.** Отдельные registry per-environment (dev/stg/prod), per-region или
per-domain. У каждой **свой `_schemas`**, следовательно, **своё независимое ID-пространство.**

> **Correction to a common slide.** Schema ID уникален в пределах одного топика `_schemas`, а **не**
> глобально во вселенной. Одна и та же Avro-схема может быть ID 42 в dev и ID 7 в prod. Как следствие,
> **нельзя** промоутить сообщения между средами по ID — на той стороне этот ID означает другую схему или
> никакую. При миграции ты пере-регистрируешь схему, и serde подставляет локальный ID.

Confluent решает межрегистровое перемещение двумя механизмами: **Schema Linking** (репликация subject'ов
между registry, например prod → DR) и **IMPORT mode** (регистрация с сохранением исходного ID, чтобы
ID-пространства совпали после миграции).

Связь registry с кластером существует только через storage-топик `_schemas`, что даёт две топологии: одна
registry на несколько app-кластеров (общий governance, единый blast radius) или своя registry на кластер
(изоляция ценой дублирования схем и ID-пространств).

## 8. Отличия от идеального мира

Точки, где реальный деплой расходится с чистой картинкой из учебника:

1. **Дефолтный replication factor топика `_schemas` рассчитан на кластер.** Confluent Schema Registry по
   умолчанию ставит `kafkastore.topic.replication.factor` в 3. На одноузловом брокере создание этого
   топика повиснет. Ставь `1`.

   > **Correction to a common slide.** Это тот же класс бага, что `__transaction_state` на одном брокере:
   > внутренний топик, у которого дефолтный replication factor превышает число брокеров, из-за чего
   > старт тихо блокируется, пока не переопределишь значение.

2. **Schema Registry — клиент брокера.** На SASL/PLAIN-кластере ему нужен свой principal и ACL
   (produce/consume на `_schemas` плюс его consumer group). Провижёнь это как код, а не руками.

3. **Apache Kafka не поставляет Schema Registry.** Его нужно ставить отдельно — Confluent Schema Registry
   (standalone), Apicurio или Karapace. На чистом Apache-кластере его отсутствие — свойство дистрибутива,
   а не сломанная установка.
