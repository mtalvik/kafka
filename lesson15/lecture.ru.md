# Lesson 15 — Kafka Streams

Предыдущие уроки строили низкоуровневых клиентов вручную: Producer, который
отправляет записи, Consumer, который делает poll и коммитит оффсеты, а вокруг
них транзакции, схемы и админская обвязка. Любой нетривиальный конвейер поверх
этих клиентов в итоге переизобретает одну и ту же машинерию: забрать батч,
преобразовать, отправить результат в другой топик, управлять consumer group,
держать локальный агрегат, восстановить этот агрегат после падения. Kafka
Streams — библиотека, которая эту машинерию упаковывает.

Это **библиотека, а не кластер**. Никакого Streams-сервера разворачивать не
надо. Добавляешь `kafka-streams` в приложение, описываешь топологию обработки и
запускаешь её внутри своего процесса. Под капотом всё построено прямо на
знакомых Producer и Consumer — никакого магического слоя, просто Consumer,
питающий граф обработчиков, которые питают Producer, плюс механизм состояния и
восстановления, положенный на топики Kafka.

## Место в ряду

Стриминговые фреймворки разменивают мощность на операционную простоту. Spark и
Flink — отдельные кластеры, которым скармливают задачи: максимум мощности,
максимум операционного веса. Написанный руками Kafka Consumer — противоположность:
запускать тривиально, но всё строишь сам. Kafka Streams занимает полезный угол:
по простоте близок к Consumer (это просто библиотека в твоём сервисе), но со
встроенной мощностью — stateful-операции, соединения, оконность, exactly-once —
достаточной для большинства задач потоковой обработки без поднятия второго
кластера.

Практическое правило: бери Streams, когда работа естественно живёт *внутри*
Kafka-native сервиса, а вход и выход — топики Kafka. Бери Flink/Spark, когда
нужен общий кластер задач, не-Kafka источники и приёмники в масштабе или очень
большое оконное состояние на много задач.

## Топология: граф обработки

Streams-приложение — это **топология**, направленный ациклический граф (DAG) из
узлов-обработчиков. Три роли узлов:

- **Source processor** — читает из одного или нескольких входных топиков, подаёт
  записи в граф. Родителя нет.
- **Stream processor** — промежуточный узел: filter, map, join, aggregate. Один
  или несколько родителей, один или несколько потомков.
- **Sink processor** — пишет записи в выходной топик. Потомков нет.

Поскольку это DAG, а не прямая цепочка, одна запись может разойтись по
нескольким веткам (записаться в топик *и* напечататься *и* пойти в агрегацию
ниже), а несколько потоков — слиться в один узел.

```
              src-topic
                  |
             [ source ]
                  |
             [ toUpper ]-----> [ print ]   (боковая ветка, терминальная)
                  |
              [ sink ]
                  |
              out-topic
```

Граф описывается через DSL (`StreamsBuilder`, `KStream`, `KTable`) либо на
самом низком уровне через Processor API. DSL компилируется в топологию
Processor API.

## Два API: DSL и Processor API

**DSL** — высокоуровневая декларативная поверхность: `filter`, `mapValues`,
`join`, `groupByKey().count()`. Именно им пользуешься в 95% случаев.

**Processor API** — низкоуровневая поверхность: реализуешь `Processor` (или
`FixedKeyProcessor`), получаешь `ProcessorContext` и делаешь `forward` вручную.
Нужен, когда DSL не выражает требуемое — кастомный доступ к состоянию,
punctuation по таймеру, форвард конкретным потомкам.

> **Correction to a common slide.** Старый материал вводит низкоуровневый узел
> через `Transformer` / `ValueTransformer` и `stream.transform(...)` /
> `transformValues(...)`. **Этот API удалён в Kafka 4.0** (deprecated в 3.3,
> KIP-820). Против клиента 4.x он не скомпилируется. Используй пакет
> `org.apache.kafka.streams.processor.api`:
>
> - `process(ProcessorSupplier, storeNames...)` — полный
>   `Processor<KIn,VIn,KOut,VOut>`, может менять ключ через
>   `record.withKey(...)`.
> - `processValues(FixedKeyProcessorSupplier, storeNames...)` —
>   `FixedKeyProcessor<KIn,VIn,VOut>`, только значение, ключ сохраняется (то
>   есть репартиционирование **не** форсируется — см. раздел про соединения).
>
> Минимальный value-only процессор:
>
> ```java
> stream.processValues(() -> new FixedKeyProcessor<String, String, String>() {
>     public void process(FixedKeyRecord<String, String> record) {
>         context.forward(record.withValue(record.value().toUpperCase()));
>     }
>     private FixedKeyProcessorContext<String, String> context;
>     public void init(FixedKeyProcessorContext<String, String> ctx) { this.context = ctx; }
> });
> ```

## Serde

Каждая запись, пересекающая границу топика — входного, выходного или
внутреннего changelog/repartition — должна быть сериализована. Streams работает
в терминах **Serde**: пары `Serializer` + `Deserializer` для одного типа.
`Serdes.String()`, `Serdes.Integer()`, `Serdes.Long()`, `Serdes.ByteArray()`
покрывают примитивы; для доменных объектов подставляешь свой (JSON или
Avro/Schema Registry, что связывает с уроком 11).

Serde задаются в двух местах: дефолтные key/value в `StreamsConfig`
(`DEFAULT_KEY_SERDE_CLASS_CONFIG` / `DEFAULT_VALUE_SERDE_CLASS_CONFIG`) и
пооперационные переопределения через `Consumed.with(...)`, `Produced.with(...)`,
`Grouped.with(...)`, `Materialized.with(...)`, `Joined.with(...)`. Когда
операция меняет тип ключа или значения, передавай подходящий Serde явно прямо в
этой операции — надежда на дефолт это самая частая причина
`ClassCastException` в рантайме.

## Stateless-операции

Преобразуют записи по одной, между записями ничего не хранят и ложатся ровно на
цикл Consumer→преобразование→Producer.

| Операция | Назначение |
|---|---|
| `filter` / `filterNot` | оставить / отбросить записи по предикату |
| `mapValues` | преобразовать значение, **ключ не меняется** (без репартиционирования) |
| `map` | преобразовать ключ и значение (помечает поток на репартиционирование) |
| `flatMapValues` / `flatMap` | одна запись → ноль или больше записей |
| `selectKey` | задать новый ключ (помечает поток на репартиционирование) |
| `peek` | побочный эффект на запись, запись проходит дальше без изменений |
| `foreach` | терминальный побочный эффект (запись во внешнее хранилище, лог) |
| `print` | терминальный отладочный вывод в stdout или файл |
| `merge` | объединить два потока одного типа в один |
| `to` | терминальная: записать поток в выходной топик |
| `split` | разложить поток на именованные ветки по предикатам |

Предпочитай value-only варианты (`mapValues`, `processValues`,
`flatMapValues`) везде, где ключ не меняется. Они оставляют поток на текущих
партициях; варианты, меняющие ключ (`map`, `selectKey`, `flatMap`, `process`),
помечают поток как требующий репартиционирования, а это лишний внутренний топик
в тот момент, когда за ними идёт stateful-операция.

### Разбор примера: обработка продажи

Событие продажи несёт номер кредитной карты, дисконтную карту, сумму, отдел и
идентификатор работника. Первый проход целиком stateless:

- **замаскировать номер карты** — `mapValues`, чтобы сырой PAN не попал ни в
  один топик ниже по потоку;
- **начислить бонусы за покупку** — `mapValues` для расчёта баллов, `to` в топик
  бонусов;
- **отследить факт продажи** — `mapValues` в представление для паттернов, `to` в
  топик паттернов;
- **сохранить замаскированную транзакцию** — `to` в топик хранения.

Добавь `filter`, чтобы оставить только дорогие покупки перед приёмником «крупные
траты», и `selectKey`, чтобы переключить ключ на нужный приёмнику.

Чтобы развести продажи кафе и электроники по разным топикам, используется
`split`:

> **Correction to a common slide.** Старый материал показывает
> `KStream.branch(Predicate...)`, возвращающий массив `KStream[]`. **Этот API
> удалён в Kafka 4.0** (deprecated в 2.8, KIP-418). Используй `split()`, который
> возвращает `BranchedKStream`, и добавляй именованные ветки:
>
> ```java
> Map<String, KStream<String, Sale>> branches = maskedStream
>     .split(Named.as("dept-"))
>     .branch((k, v) -> v.department().equals("cafe"),
>             Branched.as("cafe"))
>     .branch((k, v) -> v.department().equals("electronics"),
>             Branched.as("electronics"))
>     .defaultBranch(Branched.as("other"));
> // branches.get("dept-cafe"), branches.get("dept-electronics"), ...
> ```
>
> Либо обрабатывай каждую ветку на месте через
> `Branched.withConsumer(ks -> ks.to(...))`. Закрывай split через
> `defaultBranch(...)` или `noDefaultBranch()`.

Наконец, чтобы отдать каждую запись одного продавца во внешнюю базу — `foreach`,
терминальный узел, побочный эффект которого и есть внешняя запись.

## Состояние

Всё выше — stateless: каждое событие обрабатывается само по себе. Состояние
нужно ровно тогда, когда результат зависит от записей, увиденных *раньше*:
накопление суммы бонусов клиента для пороговой скидки, подсчёт событий по ключу
или соединение двух потоков (join обязан помнить одну сторону, пока ждёт
вторую).

Состояние порождает проблему распределения. Streams-приложение обычно работает в
нескольких экземплярах ради пропускной способности и отказоустойчивости. Каждый
экземпляр запускает один или несколько **StreamThread**, а работа делится на
**Task** — по одному Task на входную партицию. Каждый Task владеет **своим**
state store, отображённым на соответствующую партицию подкладывающего топика.
Отсюда два следствия:

1. **Всё, что участвует в одном агрегате, должно лежать в одной партиции.** Если
   события клиента размазаны по партициям, ни один Task никогда не видит клиента
   целиком, и итог по клиенту неверен. Состояние корректно только тогда, когда
   партиционировано по тому же ключу, по которому ведётся.

2. **Репартиционируй, когда ключ на входе неправильный или отсутствует.** Если у
   входа нет ключа (записи разбросаны по партициям) или ключ не тот, по которому
   агрегируешь, записи надо переложить так, чтобы совместно агрегируемые попали
   в одну партицию. `repartition()` пишет во внутренний топик с нужным ключом и
   читает обратно; `StreamPartitioner` даёт контроль над функцией партиционирования,
   когда дефолтный хеш не подходит.

```
вход (полезного ключа нет)        репартиционирование по customerId
+---+---+---+---+                 +----------+----------+
| p0| p1| p2| p3|   --repartition--> | cust A,C | cust B,D |
+---+---+---+---+                 +----------+----------+
 события разбросаны               каждый клиент теперь в одной партиции
```

Операции DSL, меняющие ключ (`selectKey`, `map`, `flatMap`, `process`), ставят
внутренний флаг «нужно репартиционирование». Когда дальше идёт **соединение,
группировка или агрегация**, Streams вставляет репартиционный топик
**автоматически** — `repartition()` в этом случае вызывать не надо. Value-only
операции флаг не ставят.

### Создание state store

```java
StreamsBuilder builder = new StreamsBuilder();

String storeName = "rewardsPointsStore";
StoreBuilder<KeyValueStore<String, Integer>> storeBuilder =
    Stores.keyValueStoreBuilder(
        Stores.persistentKeyValueStore(storeName),   // supplier
        Serdes.String(),                              // key serde
        Serdes.Integer());                            // value serde

builder.addStateStore(storeBuilder);

// привязка store к процессору по имени:
stream.process(() -> new RewardProcessor(storeName), storeName);
```

Внутри процессора store достаётся через `context.getStateStore(storeName)`:
читаешь текущую сумму, прибавляешь новые баллы, пишешь обратно и форвардишь
обогащённую запись.

> **Correction to a common slide.** Класс билдера — **`StreamsBuilder`** (во
> множественном числе, «Streams»), а не `StreamBuilder`. Методы работы со store
> на нём же: `builder.addStateStore(...)`.

### Виды хранилищ

- `Stores.persistentKeyValueStore(name)` — на **RocksDB**, сбрасывается на
  локальный диск, тянет состояние, которое не влезло бы в heap. Дефолтный и
  правильный выбор для большинства stateful-приложений.
- `Stores.inMemoryKeyValueStore(name)` — только heap, самый быстрый, ограничен
  RAM.
- `Stores.lruMap(name, maxEntries)` — в памяти с вытеснением по LRU.

Все три остаются отказоустойчивыми при включённом журналировании (ниже):
локальный store одноразовый, потому что истина лежит в changelog-топике.

### Отказоустойчивость и локальность

Два свойства делают состояние Streams пригодным для прода:

- **Локальность.** Store живёт рядом с обработчиком (heap процесса или локальный
  RocksDB), а не в удалённой базе. Чтения и записи не ходят по сети и не зависят
  от доступности внешнего сервиса.
- **Восстановление.** Каждый store подкреплён сжимаемым **changelog-топиком** в
  Kafka. Любая запись в store пишется и в changelog. Если экземпляр упал, другой
  экземпляр проигрывает changelog для этой партиции, перестраивает store и
  продолжает работу. Имя changelog: `<application.id>-<store-name>-changelog`.

Журналирование (changelog) **включено по умолчанию**. Управление на
`StoreBuilder`:

- `withLoggingDisabled()` — без changelog; состояние теряется при падении.
  Только для состояния, которое тривиально пересчитывается.
- `withLoggingEnabled(Map<String,String> topicConfig)` — настройка
  changelog-топика (retention, компакция, размер сегмента). Ключи из
  `TopicConfig`.

> **Single-node lab trap (recurring).** Streams создаёт свои внутренние топики —
> changelog **и** repartition — автоматически. Их replication factor берётся из
> `StreamsConfig.REPLICATION_FACTOR_CONFIG` (`"replication.factor"`), у которого
> дефолт **-1**, то есть «взять `default.replication.factor` брокера». На
> одноузловом лабораторном брокере создание топика с RF > 1 не проходит, и
> Streams виснет на старте ровно так же, как `__transaction_state` в уроке про
> транзакции и `_schemas` в уроке про Schema Registry. **Задавай явно:**
>
> ```java
> props.put(StreamsConfig.REPLICATION_FACTOR_CONFIG, 1);
> ```

## KStream против KTable

Два способа трактовать записи в топике:

- **KStream** — неограниченный **поток независимых событий**. Каждая запись это
  случившийся факт. «Произошла покупка X.» Ничего не перезаписывается.
- **KTable** — **changelog-представление**: каждая запись это **upsert** для
  своего ключа. Таблица держит последнее значение на ключ; новая запись с
  существующим ключом заменяет старую; значение `null` это удаление
  (tombstone). «Текущий баланс бонусов клиента C равен 340.»

`builder.stream(topic)` даёт KStream; `builder.table(topic)` даёт KTable.
`GlobalKTable` (`builder.globalTable`) — KTable, полностью реплицированный на
каждый экземпляр, удобен как небольшая справочная таблица, к которой можно
присоединяться без репартиционирования.

Преобразование в обе стороны: `stream.groupByKey().aggregate(...)` даёт KTable;
`table.toStream()` даёт KStream событий изменения.

## Группировка, оконность и агрегация

Агрегация — stateful-свёртка записей с общим ключом:

```java
KGroupedStream<String, Event> grouped = events.groupByKey();
// либо .groupBy((k, v) -> newKey, Grouped.with(...)) для смены ключа (репартиционирует)
```

Над **неограниченной** группировкой `count()` / `reduce()` / `aggregate()` дают
KTable по ключу записи. Но поток событий бесконечен — обычно агрегат нужен по
**окну** времени, а не по всей истории. Виды окон:

- **Tumbling** (кувыркающиеся) — фиксированный размер без перекрытия
  (`TimeWindows.ofSizeAndGrace`). «Счёт по минутным корзинам.»
- **Hopping** (прыгающие) — фиксированный размер с перекрытием, сдвиг меньше
  размера.
- **Sliding** (скользящие) — окно задаётся разницей во времени между записями.
- **Session** (сессионные) — динамические: окно живёт, пока записи приходят в
  пределах *интервала неактивности*, и закрывается, когда интервал истёк без
  новых записей. Длина сессии определяется данными, а не задана заранее.

Оконная агрегация ключуется по `Windowed<K>` (ключ плюс границы окна), поэтому
результат это `KTable<Windowed<K>, V>`.

### Сессионные окна (на них построено ДЗ)

Домашнее задание — *посчитать события с одинаковым ключом в пределах
5-минутной сессии* — это сессионный count:

```java
KTable<Windowed<String>, Long> counts = builder
    .stream("events", Consumed.with(Serdes.String(), Serdes.String()))
    .groupByKey()
    .windowedBy(SessionWindows.ofInactivityGapAndGrace(
            Duration.ofMinutes(5),      // интервал неактивности: 5 мин
            Duration.ofMinutes(1)))     // grace для опоздавших записей
    .count(Materialized.as("events-session-counts"));

counts.toStream()
      .foreach((windowedKey, count) ->
          System.out.printf("key=%s window=[%s..%s] count=%d%n",
              windowedKey.key(),
              windowedKey.window().startTime(),
              windowedKey.window().endTime(),
              count));
```

Сессия для ключа открывается на первом событии, продлевается каждый раз, когда
следующее событие этого ключа приходит в пределах 5 минут от предыдущего, и
закрывается, когда 5 минут прошли без новых событий по этому ключу. Сессии,
разделённые паузой больше 5 минут, — разные окна с разными счётчиками.

> **Correction to a common slide.** Старый материал строит сессионные окна через
> `SessionWindows.with(Duration)`. Эта фабрика устарела; используй
> **`SessionWindows.ofInactivityGapAndGrace(gap, grace)`** (или
> `ofInactivityGap(gap)`), где grace задан явно. То же самое относится к
> `TimeWindows.ofSizeAndGrace` и `JoinWindows` ниже — все современные фабрики
> требуют явный grace period.

## Соединения

Join комбинирует записи двух потоков (или потока и таблицы) по ключу. Похоже на
JOIN из SQL, но входы неограниченны, поэтому stream-stream join всегда
**оконный**: две записи соединяются, только если ключи совпали *и* их
таймстампы попали в окно соединения. Join «по всей таблице» для бесконечного
потока невозможен.

Три варианта:

- `join` — inner: результат только когда совпадающий ключ есть в **обоих**
  потоках внутри окна.
- `leftJoin` — все записи слева плюс совпадения справа (правая сторона может
  быть null).
- `outerJoin` — все записи с обеих сторон; совпавшие внутри окна объединяются.

Логика объединения — `ValueJoiner`:

```java
interface ValueJoiner<V1, V2, VR> {
    VR apply(V1 value1, V2 value2);
}
```

Окно:

```java
JoinWindows window =
    JoinWindows.ofTimeDifferenceAndGrace(
        Duration.ofMinutes(20),   // записи в пределах 20 мин друг от друга совпадают
        Duration.ofMinutes(5));   // grace для опоздавших
```

### Разбор примера: купон на бесплатный кофе

Выдать купон клиенту, который купил электронику **и** сделал заказ в кафе в
пределах 20 минут. Два топика — покупки электроники и заказы кафе — ключуются по
клиенту и соединяются:

```java
electronics.join(
    cafe,
    (electronicsSale, cafeOrder) -> new Coupon(cafeOrder.customerId()),
    JoinWindows.ofTimeDifferenceAndGrace(Duration.ofMinutes(20), Duration.ofMinutes(5)),
    StreamJoined.with(Serdes.String(), electronicsSerde, cafeSerde))
  .to("coupons");
```

Поскольку stream-stream join требует, чтобы обе стороны были со-партиционированы
по ключу соединения, а исходные топики ключуются иначе (или не ключуются вовсе),
`selectKey` перед join задаёт ключ соединения — и Streams вставляет репартиционные
топики автоматически, как описано в разделе про состояние. Это и есть
«автоматическое репартиционирование»: любая операция со сменой ключа, за которой
следует соединение / группировка / агрегация, запускает его без явного вызова
`repartition()`.

## Время в потоке

Окна и соединения зависят от того, *какой* таймстамп несёт запись. Источники
времени:

1. **Из события** — таймстамп записи, который мог быть выставлен продюсером при
   отправке, клиентской библиотекой или проставлен брокером при приёме
   (`message.timestamp.type` = `CreateTime` или `LogAppendTime`); либо таймстамп,
   извлечённый из содержимого.
2. **Из часов обработки** — локальное время в момент обработки записи.

Настраивается через `TimestampExtractor` (задаётся на `Consumed` или как дефолт
в `StreamsConfig`):

- **`FailOnInvalidTimestamp`** — дефолт; берёт таймстамп записи, падает на
  отрицательном или некорректном.
- **`LogAndSkipOnInvalidTimestamp`** — логирует и отбрасывает записи с
  некорректным таймстампом.
- **`UsePreviousTimeOnInvalidTimestamp`** — подставляет последнее корректное
  время.
- **`WallclockTimestampExtractor`** — игнорирует таймстамп записи и берёт время
  обработки. Выбирай только когда event time для задачи бессмысленно; оконность
  становится недетерминированной при переобработке.

Первые три наследуют `ExtractRecordMetadataTimestamp` (event time), последний —
processing time. Для ДЗ с сессионными окнами правильно event time
(`FailOnInvalidTimestamp`, дефолт): консольный продюсер проставляет каждой записи
`CreateTime`, а сессии меряются в event time.

## Ключевые тезисы

- Kafka Streams — **библиотека** поверх Producer/Consumer, выражающая работу как
  **топологию** (DAG) из source/stream/sink обработчиков.
- **Stateless**-операции (`filter`, `mapValues`, `flatMap`, `selectKey`,
  `split`, `merge`, `peek`, `foreach`, `to`) ложатся на цикл преобразования.
  Предпочитай value-only варианты, чтобы избежать репартиционирования.
- **Состояние** живёт в локальных store (RocksDB / in-memory), партиционировано
  по Task, надёжно за счёт **changelog-топиков**. Совместно агрегируемые записи
  обязаны быть в одной партиции — репартиционируй, когда ключа нет или он не
  тот.
- **KStream** = поток событий; **KTable** = upsert/changelog-представление.
  Оконная агрегация над `KGroupedStream` даёт `KTable<Windowed<K>, V>`.
- **Сессионные окна** (`ofInactivityGapAndGrace`) группируют события по ключу
  через интервал неактивности — механизм, на котором построено ДЗ.
- **Соединения** потоков оконные (`ofTimeDifferenceAndGrace`), объединяются
  через `ValueJoiner` и запускают автоматическое репартиционирование после смены
  ключа.
- **Время** по умолчанию event time (`FailOnInvalidTimestamp`); окна и
  соединения корректны ровно настолько, насколько корректны таймстампы записей.
- На **одноузловом брокере** ставь `replication.factor=1` в `StreamsConfig`,
  иначе создание внутренних топиков виснет на старте.
