# Потоковая обработка и модель Dataflow

## 1. Область

Это концептуальный урок, а не лаба на брокере. Цель — собрать словарь, на котором построен любой движок потоковой обработки, включая Kafka Streams: неограниченные данные, время события против времени обработки, окна, водяные знаки, триггеры и то, как уточняются частичные результаты. Apache Beam взят как эталонный API, потому что он выражает эти понятия напрямую и чисто; сами понятия переносятся на Kafka Streams, Flink и Spark Structured Streaming под другими именами.

## 2. Ограниченность/неограниченность, а не «batch/streaming»

**Поток данных** (event stream) — абстрактное представление *неограниченного* набора данных: потенциально бесконечного по размеру, непрерывно растущего.

Полезное различие — **ограниченные vs неограниченные** данные, а не batch vs streaming. Batch и streaming — свойства *движка исполнения*, а не данных. Неограниченные данные десятилетиями обрабатывались повторными batch-прогонами, а грамотно построенный потоковый движок без проблем обрабатывает ограниченные данные. Оставь «batch» и «streaming» для рантаймов; для данных используй «ограниченные/неограниченные».

## 3. Свойства потока

- **Неизменяемость / append-only.** Поток — это append-only лог. Однажды записанное событие не меняется; оно является источником истины.
- **Воспроизводимость — с оговоркой.** Поток можно перечитать с более ранней точки для восстановления состояния или построения новых представлений, *пока данные ещё хранятся*. Воспроизводимость — функция retention, а не врождённая гарантия.
- **Неограниченность.** Потенциально бесконечен, непрерывно растёт — именно поэтому и существует оконность.
- **Непрерывность / низкая задержка.** Обрабатывается по мере поступления записей, а не по расписанию.

> **Correction to a common slide.** «Упорядоченность (строгий порядок, гарантирующий консистентность)» — *не* внутреннее свойство потока. Порядок соблюдается только *внутри одной партиции / по ключу*. По потоку в целом события, как правило, **неупорядочены по времени события** — это центральная посылка статьи о Dataflow («unbounded, unordered»). Если бы поток был глобально упорядочен по времени события, водяные знаки и триггеры были бы не нужны. Они существуют именно потому, что это не так.

> **Correction to a common slide.** «exactly-once» не место в списке *врождённых* свойств потока. Это трудно достижимая гарантия доставки, которой у многих систем исторически не было (Storm, Samza, Pulsar выходили без неё). Это свойство *конвейера обработки*, достигаемое усилиями, а не то, чем поток обладает по природе.

## 4. Парадигмы обработки

| Парадигма | Ключевое свойство | Задержка | Применение (2026) |
|---|---|---|---|
| Запрос / Ответ | синхронность, предсказуемый P99, non-blocking I/O | < 100 мс | онлайн-транзакции, UI, инференс моделей |
| Пакетная (Batch) | пропускная способность, детерминизм | секунды–минуты | ETL, отчёты, обучение ML |
| Потоковая (Streaming) | непрерывность, состояние, exactly-once | секунды и меньше | реалтайм-аналитика, аномалии, EDA |
| Гибридная / Унифицированная | единый движок, материализованные представления | почти непрерывно | Kappa-платформы, интерактивная аналитика |

«exactly-once» в строке Streaming — *цель, к которой движок стремится*, а не подарок; см. поправку выше.

**Как читать таблицу.** Парадигмы различаются по двум осям: *единица работы* (сколько обрабатываем за раз) и *кто ждёт*.

- **Запрос / Ответ** — один запрос, один немедленный ответ; вызывающий *блокируется* до возврата. REST-вызов или запрос к БД. Единица работы: один запрос.
- **Batch** — собрать большую *ограниченную* кучу данных и обработать её всю разом, по расписанию; живьём никто не ждёт. Ночной ETL. Единица работы: весь датасет.
- **Streaming** — обрабатывать каждое событие *по мере поступления*, непрерывно, храня состояние между событиями; джоба никогда не «заканчивается». Скоринг фрода на живом потоке кликов. Единица работы: одно событие.
- **Гибрид / Унифицированная** — один движок держит постоянно обновляемый результат, который ещё и можно запросить как таблицу; граница batch/stream исчезает. Единица работы: материализованное представление, которое держат свежим.

## 5. Два домена времени

Каждое событие несёт два времени:

- **Время события (event time)** — когда событие фактически произошло, у источника.
- **Время обработки (processing time)** — когда конвейер его увидел.

Время события практически никогда не меняется. Время обработки постоянно идёт вперёд. Разрыв между ними — **skew** (processing-time lag / event-time skew), и он динамический: растёт, когда конвейер отстаёт, и сокращается, когда догоняет. Синхронизация часов в распределённой системе не предполагается. Надёжный анализ ведётся во *времени события*; время обработки — это лишь «когда мы это увидели».

## 6. Модель Dataflow: четыре вопроса

Модель раскладывает любой конвейер на четыре независимых измерения:

- **Что (What)** вычисляется → трансформации (`ParDo`, `GroupByKey`, комбайнеры).
- **Где (Where)** во времени события → оконность.
- **Когда (When)** во времени обработки материализуются результаты → водяные знаки и триггеры.
- **Как (How)** ранние результаты соотносятся с поздними уточнениями → режим накопления.

Сила модели в ортогональности: меняешь *когда* выдаёшь, не трогая *что* вычисляешь; меняешь *как* уточняешь, не трогая *где* окном режешь.

## 7. Оконность (the "Where")

Оконность нарезает неограниченный набор данных на конечные куски, чтобы группирующие операции (агрегация, джойны) могли завершиться.

- **Фиксированное / tumbling** — статический размер; частота равна длине. Суточные, часовые.
- **Скользящее / sliding** — фиксированные размер и период, причём период < размера, так что окна перекрываются. Фиксированное — частный случай, где период = размер.
- **Сессии / sessions** — динамическое, по ключу, ограничено промежутком бездействия (gap). События ближе друг к другу, чем gap, сливаются в одну сессию.

Окна также **выровненные** (применяются ко всем данным этого диапазона времени) или **невыровненные** (к подмножеству, например по ключу). Сессии по природе невыровненные. Нативная поддержка невыровненных окон по времени события — главный вклад модели Dataflow по сравнению с ранними системами.

## 8. Водяные знаки (часть "When")

**Водяной знак (watermark)** — монотонно возрастающая, обычно *эвристическая* оценка прогресса по времени события: нижняя граница, утверждающая «мы считаем, что все события с временем события ≤ W уже наблюдались».

> **Correction to a common slide.** Водяной знак — это **не** «временная метка самого старого ещё не обработанного события». Это *нижняя граница полноты по времени события*, и она, как правило, эвристическая. Ключевое: **опоздавшие данные могут приходить и приходят позади водяного знака** — конвейер продвинул W за точку во времени события до того, как для этой точки появился отстающий. Водяной знак — оценка прогресса, а не гарантия полноты. (Собственная диаграмма слайда говорит «monotonically advancing estimate of event-time progress» — буллет противоречит диаграмме.)

У водяных знаков два режима отказа, поэтому их никогда не используют в одиночку:

- **Слишком быстрый** — опоздавшие данные приходят позади него, поэтому полагаться только на него ломает 100% корректность.
- **Слишком медленный** — один отстающий держит глобальную метрику, раздувая задержку для всего.

## 9. Триггеры и уточнение (остаток "When" + "How")

**Триггер** решает, *когда* текущее содержимое окна выдаётся как *pane* (панель). Частые условия триггера:

- **На каждом элементе** — `Repeatedly.forever(AfterPane.elementCountAtLeast(1))`.
- **На интервалах времени обработки** — периодическое срабатывание.
- **Когда водяной знак проходит конец окна** — по умолчанию, «мы считаем окно завершённым».

> **Correction to a common slide.** Срабатывание на каждом элементе — это **не** «ParDo». `ParDo` — это *трансформация* (это «Что»), а не триггер. Триггера под именем ParDo не существует. Поэлементный вывод в Beam — это `Repeatedly.forever(AfterPane.elementCountAtLeast(1))`. Смешивать эти два — путать оси *Что* и *Когда*.

**Режим уточнения** (это «Как») решает, как соотносятся последовательные panes одного окна:

- **Discarding** — содержимое окна сбрасывается после срабатывания; каждая панель независима (дельты).
- **Accumulating** — содержимое сохраняется; каждая панель уточняет предыдущую (для sink-ов с перезаписью).
- **Accumulating & retracting** — как accumulating, но перед новым значением выдаётся *ретракция* предыдущего. Нужна, когда нижестоящий `GroupByKey` иначе мог бы задвоить уточнённые результаты на разных ключах.

## 10. Разбор примера (Beam API)

Суточная сумма по ключу: on-time результат в конце дня и уточнённый результат, если опоздавшие данные пришли в течение часа:

```java
PCollection<KV<String, Long>> dailyReport = transactions
    .apply(Window.<KV<String, Long>>into(FixedWindows.of(Duration.standardDays(1)))
        .triggering(
            AfterWatermark.pastEndOfWindow()
                .withLateFirings(AfterPane.elementCountAtLeast(1)))  // перезапуск на опоздавших
        .withAllowedLateness(Duration.standardHours(1))
        .accumulatingFiredPanes())
    .apply(Sum.longsPerKey());
```

*«В 00:00 сформирован отчёт; в 00:30 пришли опоздавшие данные — что будет?»* При наличии `.withLateFirings(...)` и `allowedLateness = 1ч` срабатывает вторая, уточнённая панель, содержащая данные первого отчёта плюс опоздавшие записи. Именно режим **accumulating** делает вторую панель надмножеством, а не голой дельтой.

> **Correction to a common slide.** Уточнённый отчёт в 00:30 **не** возникает автоматически из одного лишь `AfterWatermark.pastEndOfWindow()`. Этот триггер по умолчанию срабатывает *один раз* на водяном знаке. Без явного `.withLateFirings(...)` опоздавшие данные буферизуются (в пределах `allowedLateness`), но вторая панель не выдаётся. Позднее срабатывание нужно объявить.

> **Correction to a common slide.** `Sum.bigDecimalsPerKey()` в Beam **не существует** — `Sum` покрывает только `Integer`, `Long`, `Double`. Для `BigDecimal` нужен собственный `Combine.perKey(...)` со своим `CombineFn`. Кроме того, цепочка `.apply(GroupByKey.create()).apply(Sum.…PerKey())` ломается по типам: комбайнер `…PerKey` группирует внутри себя, поэтому после явного `GroupByKey` ты передаёшь `KV<K, Iterable<V>>` туда, где ждут `KV<K, V>`. Используй либо один комбайнер (`Sum.longsPerKey()`), либо `GroupByKey` с ручной суммой в `ParDo` — но не оба сразу.

## 11. Таблично-потоковый дуализм

У одних и тех же данных два прочтения:

- **Поток** — каждая запись это независимый, автономный факт в неограниченном наборе.
- **Таблица** — каждая запись это *обновление*; значение — последнее состояние для ключа (changelog).

Таблица — накопленное состояние потока; поток — changelog таблицы. Прочитанное как поток `("alice",1) ("charlie",1) ("alice",2) ("bob",1)` даёт четыре факта; свёрнутое в таблицу по ключу даёт текущее состояние `{alice:2, charlie:1, bob:1}`. Этот дуализм — основа разделения `KStream` / `KTable` в Kafka Streams и систем материализованных представлений в целом.

## 12. Паттерны потоковой обработки

- **Трансформация** — переформатирование событий в другой формат/схему/протокол по пути в другую систему (Camel, ksqlDB).
- **Фильтры и пороги** — пропускать только события, удовлетворяющие предикату (`brand == "Toyota" AND year > 2010`).
- **Оконная агрегация** — шардировать по ключу, агрегировать по окну параллельно (sum, min, max, avg, stddev, count), собрать обратно.
- **Соединение потоков (stream join)** — объединять события из нескольких потоков по ключу внутри окна, в стиле SQL-join.

Помимо этих: temporal event ordering, buffered ordering, replay, snapshot-state persistence, failover — семейства надёжности и масштабирования. Четыре выше — несущие для этого курса.

## 13. Фреймворки

| Фреймворк | Лучшее для | Ключевая черта | Компромисс |
|---|---|---|---|
| Apache Flink | stateful, сложные события | современная true-streaming архитектура | крутая кривая обучения |
| Kafka Streams | тесная интеграция с Kafka | встраиваемая библиотека, низкая задержка | привязка к экосистеме Kafka |
| Spark Structured Streaming | унифицированный batch + stream | микропакетирование, MLlib | задержка выше, чем у true streaming |
| Apache Beam | кроссплатформенные пайплайны | один API, много раннеров (Flink/Spark/Dataflow) | зависит от нижележащего раннера |
| Google Cloud Dataflow | полностью managed | serverless-исполнение, автоскейлинг | vendor lock-in на GCP |

> **Correction to a common slide.** Датировка «2013 Flink» неточна. То, что стало Flink, началось как исследовательский проект *Stratosphere* (TU Berlin, примерно с 2010); проектом Apache он стал в 2014, top-level — позже в том же году. «2013 Spark Streaming и Apache Flink» сжимает две разные линии времени.

## 14. Связь обратно с Kafka

Kafka Streams реализует практическое подмножество этой модели прямо поверх Kafka: `KStream`/`KTable` — это таблично-потоковый дуализм; оконные агрегации, stream–stream и stream–table джойны, обработка по времени события с grace periods (имя Kafka для allowed lateness) — всё здесь. Обработка водяных знаков в Kafka Streams проще и основана на stream-time, а не на полной триггерной алгебре Dataflow, но ментальная модель та же: *что / где / когда / как*. Всё в этом уроке — теория за API Kafka Streams, который пойдёт следующим.
